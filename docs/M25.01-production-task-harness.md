# M25.01 — Production Task Harness Contract

## Purpose

Make real task outcomes measurable. A task is not successful merely because a model returned text, an adapter returned `EXECUTED`, or a stage trace says `COMPLETE`.

Implementation: `lib/production-task-harness.ts`  
Automated tests: `test/production-task-harness.test.ts`

## Task record contract

Each task record carries:
- immutable schema identifier: `production-task-v1`;
- task ID, title, objective, created/updated timestamps;
- explicit acceptance criteria, each with stable ID and required/optional flag;
- per-criterion status and evidence references;
- evidence records (test, artifact, source, log, API response, human review);
- artifact references;
- terminal outcome summary, failure code, and acceptance score.

## State machine

`QUEUED → ACCEPTED → RUNNING → VERIFYING → SUCCEEDED | PARTIAL | FAILED | BLOCKED`

- A verifier may return `VERIFYING → RUNNING` when a repair is needed.
- `SUCCEEDED`, `PARTIAL`, `FAILED`, and `BLOCKED` are terminal states in this initial contract.
- Illegal state transitions are rejected.
- `FAILED` requires a failure code.
- `BLOCKED` requires a reason.
- `SUCCEEDED` requires all required criteria to pass, every passed criterion to reference evidence present in the record, and a non-empty outcome summary.
- Evidence references are IDs, not claims; the task runner must persist the referenced evidence and verify artifacts before allowing success.
- This module is a deterministic domain layer. It does **not** yet persist records or expose a production task API. Do not call M25.01 production-complete until the persistence and endpoint layer are implemented and tested.

## Acceptance score

`score = round(100 × passed criteria / total declared criteria)`

This is a transparent acceptance-criteria ratio, not an AI quality score. Optional criteria remain in the denominator so the score cannot be inflated by marking difficult criteria optional after a run. Criteria must be fixed when the task is created.

## Benchmark suite T01–T10

| ID | Task | Acceptance proof | Safety boundary |
|---|---|---|---|
| T01 | Repository diagnosis | Reproducible root cause, file/line evidence, independently confirmed conclusion | Read-only until fix is approved |
| T02 | Evidence-backed research | Claims linked to sources, freshness noted, conflicting evidence called out | No invented sources or unsupported certainty |
| T03 | Small feature implementation | Diff, typecheck/lint, relevant tests, acceptance check | Isolated branch/change; no deploy before checks |
| T04 | Bug reproduction and repair | Reproduction fails before repair and passes after repair | Preserve regression test |
| T05 | Real API operation | Real response, schema validation, timeout/error path, sanitized evidence | Allowlisted endpoint; no secrets in logs |
| T06 | Artifact creation | Output exists, correct type, opens/parses, content checks pass | Do not report artifact success based on intent alone |
| T07 | Recovery and idempotency | Same key retried; one durable side effect; state can be replayed | Test only against a controlled sandbox |
| T08 | Render deployment check | Deployment commit/status, health response, request evidence agree | Render only; never infer live from build success |
| T09 | Multi-step task | At least three dependent steps, intermediate evidence, final acceptance checks | Persist checkpoints; block unsafe external actions |
| T10 | Learning loop | Same benchmark before/after a verified lesson; quality delta and regression checks | Do not label a lesson effective without measured improvement |

## Required run report

Every benchmark run must produce:
1. Task ID and versioned task definition.
2. Start/end timestamps and state transitions.
3. Acceptance criteria frozen before execution.
4. Evidence IDs and content hashes where feasible.
5. Tool/provider trace with sensitive values redacted.
6. Per-criterion pass/fail/block status.
7. Final outcome: `SUCCEEDED`, `PARTIAL`, `FAILED`, or `BLOCKED`.
8. Score and limitations.
9. Reproduction instructions.
10. Persistence confirmation when records are claimed durable.
